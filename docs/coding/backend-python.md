対象は `backend/` 配下。共通方針は [common.md](./common.md)。本ファイルはPython固有の内容のみを扱う。

各項目の状態表記は [common.md](./common.md) と同じ（確定／暫定／未決定／今後検討）。

## 1. コメント・ドキュメンテーション

**状態：確定**

### ルール

- docstringは**Googleスタイル**で書く（`Args` / `Returns` / `Raises` 等のセクション形式）。
- 関数の引数・戻り値には**型ヒント（type hints）を必ず付与する**。省略しない。

### 理由

- Googleスタイルは可読性が高く採用実績も多いため、型ヒントと合わせて引数・戻り値の説明を構造化して残せる。
- 型ヒントが唯一の「機械的に検証可能な仕様」になる。型を省略すると非自明な仕様がコードにもコメントにも残らなくなる。

### 例

```python
def lock_user(user: User) -> None:
    """連続ログイン失敗回数の上限超過時に、ユーザーを一時ロックする。

    Args:
        user: ロック対象のユーザー。
    """
    # 要件定義6.1のブルートフォース対策により、解除は時間経過のみで手動解除は設けない
    user.locked_until = datetime.now() + timedelta(minutes=15)
```

## 2. 型の扱い（型安全性）

**状態：確定**

### ルール

- mypy strict相当の設定を採用する。`Any`の使用は原則禁止。
- 外部ライブラリの型定義が無い／不正確である等の例外に限り`Any`を許可する。使用箇所には直前に1行コメントで許容理由を明記する。

### 例

```python
# 悪い例：理由なしのAny
def parse_config(raw: Any) -> dict: ...

# 良い例：外部ライブラリの型定義が存在しないため一時的にAnyを許容
# (xxx-libがv2時点で型定義未対応のため。型定義追加時に適切な型へ置き換える)
def parse_legacy_response(raw: Any) -> dict: ...
```

## 3. エラーハンドリング

**状態：確定**

### ルール

- 異常系は**例外ベース**で表現する。ドメイン例外クラスを`raise`し、FastAPIの例外ハンドラでHTTPレスポンス（`{"message": "string"}`形式）に変換する。
- 戻り値による成功/失敗表現（Result型等）は採用しない。
- 具体的な例外クラスの階層設計・HTTPステータスコードへの変換ルールは10節を参照。

### 理由

- FastAPI・Pythonの慣用的な使い方と自然に噛み合い、個人開発規模でResult型を導入するのは過剰と判断した。

## 4. ログ出力

**状態：確定**

### ルール

- 標準の`logging`モジュール＋軽量なJSONフォーマッタ（例：`python-json-logger`）を用いて構造化ログ（JSON）形式を実現する。
- ログレベルの使い分けは以下の通り。

| レベル | 用途 |
|---|---|
| DEBUG | 開発時のみの詳細情報（本番では出力しない） |
| INFO | 通常のアクセスログ（`method`/`path`/`status_code`/処理時間）、LLM呼び出しの開始・完了（モデル名・トークン数・所要時間） |
| WARNING | 想定内だが注意すべき事象（ログイン失敗、ユーザーロック発生、レート制限抵触） |
| ERROR | `AppError`系のハンドリング済み異常、外部API呼び出しの最終失敗（13節のリトライを使い切った場合） |
| CRITICAL | 使わない（このプロジェクト規模ではERRORとの区別に意味が薄いため） |

- 以下は**出力してはいけない**：パスワード（平文・ハッシュ問わず）、JWTトークンの値そのもの、その他の秘匿情報（APIキー等）。

### 理由

- Python標準のもので足り、過度な監視基盤の構築にはあたらない。
- レベルを絞ることで「何かあったらWARNING以上を見ればよい」という運用が簡潔になり、要件定義7節の「ログで状況確認できれば十分」という運用方針に合う。
- パスワード・トークン等の秘匿情報がログに残ると、ログ経由での情報漏えい経路になるため、明示的に禁止する（15節のセキュリティ方針と一貫）。

## 5. 設定値・環境変数の管理

**状態：確定**

### ルール

- 設定は`app/config/`配下に3段構成で置く。

```text
app/config/
├── settings.py    … Pydanticの`BaseSettings`。環境変数を読み込む（DB接続情報、LLM APIキー、JWT秘密鍵、機能フラグ〈サインアップ有効/無効等〉など）
├── constants.py   … 環境変数以外のハードコード値（ロック時間、失敗回数上限、ページング件数、chat_modeの値等）
└── __init__.py    … 上記2つを re-export するだけ。ロジックは持たせない
```

- アプリケーションコードは`os.environ`を直接読んだり、定数をベタ書きしたりせず、必ず`app.config`（`settings`・`constants`）経由でアクセスする。
- 環境変数・定数から加工が必要な派生値（例：文字列で受け取った設定値を別の型に変換する等）がある場合も、`__init__.py`ではなく`settings.py`／`constants.py`側で完結させる。

### 理由

- 型安全性の方針と一貫させ、設定値の一覧性とテスト時のモックしやすさを確保するため。
- 環境変数由来の値（環境ごとに変わる）とハードコードする定数（環境によらず固定）を別ファイルに分けることで、値の性質が一目で分かる。
- `app.config`という単一の入口に統一することで、将来「定数だったものを環境変数化する」といった変更があっても、呼び出し側のコードを変更せずに済む。

## 6. テスト方針

**状態：確定**

### ルール

- ビジネスロジック（ロック判定、`chat_mode`分岐、バリデーション等）は単体テストで担保する。
- 認証・チャット等、複数レイヤーをまたぐ主要フローはFastAPIの`TestClient`を用いたAPI結合テストで担保する。
- 外部LLM APIの呼び出しは常にモックする（費用・非決定性の回避のため）。
- DBはモックせず、Docker Compose上のテスト用DBに対して実際にクエリを実行する結合テストを行う。
- テストコードは`tests/`配下にソースのディレクトリ構造をミラーリングして配置する。具体的な階層は**未決定**（今後の論点）。

### 理由

- 個人開発規模で投資対効果が高い範囲（ビジネスロジック＋主要フロー）に絞りつつ、LLM呼び出しコストと非決定性は避ける。
- 既にDocker Compose環境があるため、テスト用DBを用いた結合テストの追加コストは小さい。

## 8. レイヤー構成・ディレクトリ構成

**状態：確定**

### ルール

- レイヤーは**3層**（API層／サービス層／インフラ層）とする。ユースケースとドメインロジックは分離せず、**サービス層に統合**する。
- ディレクトリ構成は以下の通り。抽象的な名称（`infra`・`external`等）は使わず、実体に即した名前にする。

```text
backend/app/
├── api/           … FastAPIルーター、リクエスト/レスポンスモデル（Pydanticスキーマ）
├── services/      … ユースケース＋ドメインロジック（サービス層）
├── models/        … SQLAlchemyモデル（テーブル定義）
├── repositories/  … DB操作（クエリ・永続化処理）
└── llm/           … LLM呼び出し（LangGraphのグラフ・ノード定義。13節参照）
```

### 理由

- 現時点で見えているビジネスロジック（ログイン失敗ロック判定、`chat_mode`分岐、簡易なバリデーション）は、独立した「ドメイン層」を必要とするほど複雑ではないため、ユースケースとドメインロジックを統合した3層とした。過剰な層構造を避けつつ、責務分離とテスト容易性（論点9のテスト方針）は確保できる。
- `models`（テーブル定義）と`repositories`（クエリ・永続化処理）は責務が異なるため分離した。`models`だけに統合すると、クエリ処理の置き場所が曖昧になる。
- `llm`は現時点で唯一の外部API連携であるため、抽象的な`external`ではなく実体に即して命名した。将来LLM以外の外部連携が増えた場合は、その時点でディレクトリ構成を見直す（YAGNI）。

## 9. Pydanticスキーマの設計方針

**状態：確定**

### ルール

- リクエスト/レスポンスは独自のPydanticスキーマとして定義し、SQLAlchemyモデル（`models/`）とは常に分離する。
- レスポンス生成時は、Pydantic v2の`model_validate(obj, from_attributes=True)`でORMオブジェクトから変換してよい。都度手動でフィールドをコピーする必要はない。
- 命名は`XxxRequest` / `XxxResponse`サフィックスで統一する。
- 基本的なデータ制約（必須、文字数、文字種等）はPydanticのフィールドバリデータ（`field_validator`）に書く。DBアクセスを伴う、または複雑なビジネスロジック（例：ログインIDの重複チェック）はスキーマのバリデータに書かず、サービス層に置く。

### 理由

- 8節（レイヤー構成）で決めたモデル/リポジトリ分離の意図（DB構造をAPIに直接晒さない）を保ちつつ、Pydantic標準機能でボイラープレートを削減できる。
- 命名規則の一貫性（論点2）に沿い、`Request`/`Response`サフィックスは用途が一目で分かる。
- Pydanticのバリデータは同期的でDBアクセスを想定しない仕組みのため、DBアクセスを要する検証や複雑な業務ルールはサービス層に置くのが自然。

## 10. 例外クラスとHTTPエラーの変換

**状態：確定**

### ルール

- 基底例外クラス `AppError(Exception)` を `app/services/exceptions.py` に定義する。個別の例外（`NotFoundError`・`ConflictError`等）はこれを継承するが、**HTTPステータスコードは持たない**。業務上の異常のみを表現する。
- API層（`app/api/`）に、例外クラスとHTTPステータスコードの対応表（マッピング辞書）を持つ。

```python
EXCEPTION_STATUS_MAP: dict[type[AppError], int] = {
    NotFoundError: 404,
    ConflictError: 409,
    UnauthorizedError: 401,
    UserLockedError: 423,
}
```

- `AppError`用の例外ハンドラを1つ定義し、上記の対応表から`status_code`を引いて、`{"message": str(exc)}`（6節の形式）をレスポンスとして返す。個別の例外ごとにハンドラは増やさない。
- 個別の例外クラスは今のうちにまとめて定義せず、実装しながら必要になった時点で追加する（マッピング辞書にも都度追記する）。

### 理由

- サービス層は「何が起きたか（業務上の異常）」だけを表現し、「それが何番のステータスコードになるか」はAPI層の責務とすることで、8節のレイヤー分離（サービス層はHTTPを意識しない）に厳密に従う。
- 例外クラスにステータスコードを持たせる案は簡潔だが、サービス層がHTTPの詳細に依存してしまうため採用しない。
- 個別クラスの先回り定義は、このプロジェクトで一貫しているYAGNI方針（6節の`code`フィールド、8節の`llm`命名等）と合わせ、実際に必要になってから追加する。

## 11. Dependency Injection

**状態：確定**

### ルール

- FastAPI標準の`Depends()`のみを使う。専用のDIコンテナライブラリ（`dependency-injector`等）は導入しない。
- DBセッション取得（`get_db()`）、サービスのインスタンス化（`get_xxx_service()`等）といった依存注入用の関数は `app/api/dependencies.py` に集約する。
- テスト時は`app.dependency_overrides`でDBセッションや外部LLMクライアントをモックに差し替える（6節のテスト方針と対応）。

### 理由

- 個人開発のMVP規模には専用DIコンテナは過剰であり、これまでの判断（YAGNI寄りの方針）と一貫する。
- FastAPI標準の`Depends()`と`dependency_overrides`だけで、DB・外部LLM APIといった「差し替えたい依存」のテスト容易性を十分に確保できる。

## 12. 非同期処理の使い方

**状態：確定**

### ルール

- エンドポイント・サービス・リポジトリ・LLM APIクライアントは**すべて`async def`で統一**する。同期・非同期を混在させない。
- DBアクセスはSQLAlchemyの非同期エンジン（`AsyncSession`）＋`asyncpg`ドライバを使う。

### 理由

- 要件定義6.4「逐次ストリーミング表示」、6.3「PERSONA_ONLYモードでの自動連続進行」はI/Oバウンドな非同期処理の恩恵を受けやすい。
- チャット機能はDB保存とLLM呼び出しが同じ処理フロー内で密接に絡むため、同期・非同期を混在させると同期呼び出しのラップ（`run_in_threadpool`等）が都度必要になり、かえって複雑になる。全体を非同期に統一した方が結果的にシンプル。
- `SQLAlchemy==2.0.49`（非同期対応済みのバージョン）が既に採用されており、追加のライブラリ変更は不要。

## 13. 外部APIアクセス（LLM呼び出し）

**状態：確定**

### ルール

- ペルソナ応答生成・応答ペルソナ選択（連鎖発言の継続判断を含む）・チャットタイトル自動生成は、**LangGraph**の`StateGraph`（`app/llm/graph.py`）として実装する。「話者選択→応答生成→タイトル更新→（継続判定）」という循環をグラフのサイクルとして表現し、PERSONA_ONLYの自動進行とUSER_PARTICIPATEDの連鎖発言は同じグラフ構造を共有する。
- チャットモデルの呼び出しは**特定のLLMプロバイダに依存しない**構成にする。`langchain`の`init_chat_model`（`app/llm/models.py`）を使い、`app.config.settings`側で`プロバイダ名:モデル名`形式の文字列（例：`openai:gpt-5-mini`）としてモデルを指定する。プロバイダを追加・変更する場合も、対応するLangChain連携パッケージ（`langchain-openai`・`langchain-anthropic`等）を`requirements/requirements.txt`に追加し、設定値の文字列を変えるだけで済むようにする。構造化出力が必要な箇所（応答ペルソナ選択・タイトル生成）は`with_structured_output`を使う。
- APIキーはプロバイダごとに`app.config.settings`へoptionalなフィールドとして追加する（例：`openai_api_key`）。全プロバイダ分を先回りして定義せず、実際に使うプロバイダが増えた時点で追加する（10節と同じYAGNIの考え方）。`app/llm/models.py`内の対応表（プロバイダ名→APIキー）もあわせて拡張する。
- リクエストスコープの依存（クライアント切断検知用の`Request`・ターン数上限・停止フラグ確認）は、LangGraphのRuntime Context API（`context_schema`・`Runtime[ChatRunContext]`）で各ノードへ注入する。チャットモデル自体はリクエストをまたいで共通のため、グラフ構築時にノードのクロージャとして注入する（`app/llm/models.py`）。
- 依存パッケージのバージョンは`requirements/requirements.txt`で固定する（`langgraph`・`langchain`・`langchain-openai`・`langchain-core`・`openai`等、利用するプロバイダの連携パッケージを含む）。
- タイムアウト・5xx・429（レート制限）等の一時的なエラーに対しては、LangGraphのノード単位`RetryPolicy`（`app/llm/retry.py`）で少数回の再試行＋指数バックオフを行う。4xxクライアントエラー（不正リクエスト等）は再試行しない。各チャットモデル自体のリトライ（`max_retries`）は無効化し、リトライ責務を`RetryPolicy`に一本化する。

### 理由

- 「話者選択→応答生成→タイトル更新」は本質的に循環のあるフローであり、LangGraphの`StateGraph`はこの種のループを自然に表現できる。素のSDK呼び出し＋手書きループより、PERSONA_ONLYとUSER_PARTICIPATEDでグラフ構造を共有しやすい（ユーザー判断により、当初想定していた「OpenAI公式SDKを直接使う薄いラッパー」方針から変更した）。
- 対話生成にはOpenAI APIを使う想定で始めたが、将来的に他社モデルも使う可能性があるため（ユーザー判断）、`init_chat_model`によりプロバイダの切り替えを設定値の変更だけで完結させ、`app/llm/`の呼び出し側コード（`graph.py`・`nodes.py`）がプロバイダを意識しないようにする。
- 外部API呼び出しの一時的な失敗は珍しくなく、軽量な再試行は費用対効果が高い。恒久的なエラー（4xx）まで再試行するのは無駄なリトライを招くため対象外とする。LangGraphの`RetryPolicy`はノード単位のリトライを標準機能として提供しており、`tenacity`を別途導入する必要がない。

### 関連事項（対象外）

- 要件定義7節の「レート制限（連続送信・短時間での連発送信の制限）」は、LLMクライアント自体ではなく、ユーザーからのAPIリクエストを制限するAPI層の関心事のため、本節では扱わない（「レート制限」として別途今後検討する）。

## 14. DBアクセス（リポジトリ層の実装パターン）

**状態：確定**

### ルール

- リポジトリは**テーブルごとにクラス**として実装する（例：`UserRepository`・`ChatRepository`）。コンストラクタで`AsyncSession`を受け取り、インスタンス変数として保持する。
- 各種DB操作（取得・作成・更新等）は、そのクラスの**メソッド**として実装する（例：`UserRepository.get_by_login_id(login_id: str) -> User | None`）。
- コミット・ロールバックはリポジトリ内では行わず、`get_db()`の依存関数内で一括管理する（正常終了時に`commit`、例外時に`rollback`）。リポジトリのメソッドは`flush`までに留める。
- クエリはSQLAlchemy 2.0スタイル（`select()` + `session.execute()`）を使う。レガシーな`session.query()`は使わない。

### 理由

- テーブルごとにクラスを分けることで、関連する操作がひとまとまりになり見通しが良くなる。
- 「1リクエスト＝1トランザクション」の原則に沿い、複数のDB更新をまたぐ処理の一貫性を保つため、コミットは`get_db()`に一元化する。
- SQLAlchemy 2.0スタイルは非同期セッション（12節）で標準的に使われる書き方であり、レガシーAPIは非同期セッションでは使えない。

## 15. セキュリティ上の注意点

**状態：確定**（②のJWT有効期限・リフレッシュトークン方針のみ**暫定**）

### ルール

- **パスワードハッシュ**：`argon2-cffi`（Argon2id）を使う。
- **JWT・Cookie**：ライブラリは`pyjwt`、署名方式は`HS256`（秘密鍵は5節の`BaseSettings`経由）。Cookie属性は`HttpOnly`・`Secure`（本番HTTPS前提）・`SameSite=Lax`。有効期限は暫定で24時間とし、リフレッシュトークンは導入しない（MVPスコープ外）。
- **CSRF対策**：`SameSite=Lax`のCookie属性に加え、状態変更リクエスト（POST/PUT/DELETE等）では`Origin`ヘッダーを検証する。専用のCSRFトークン機構（二重送信Cookie等）は現時点では導入しない。
- **インジェクション対策**：14節で決めたSQLAlchemy 2.0スタイルのクエリのみを使用し、生SQL文字列の組み立て（f-string等でのSQL直接構築）は禁止する。

### 理由

- Argon2idはOWASPのパスワード保存ガイドラインで第一推奨とされるアルゴリズムであり、bcryptより新しい水準の安全性を持つ。
- Next.jsフロントとFastAPIバックエンドが同一サイト運用で、外部フォームから叩かれることを想定しない構成のため、`SameSite=Lax`＋`Origin`ヘッダー検証で実用上十分なCSRF対策になる。専用トークンは多層防御としては有効だが、この脅威モデルに対しては過剰と判断した（クロスサイト構成が必要になった時点で再検討＝YAGNI）。
- 生SQLの組み立てを禁止することで、SQLインジェクションのリスクを構造的に排除する。

## 16. レート制限（連続送信対策）

**状態：確定**

### ルール

- `slowapi`（インメモリバックエンド）を使う。Redis等の外部ストアは導入しない。
- カウントの単位：
  - 認証必須のエンドポイント（メッセージ送信等）は`user_id`（JWTから取得）単位。
  - 未認証のエンドポイント（サインアップ）はIPアドレス単位。
  - ログインは対象外（既存のアカウントロック機構〈15節〉が同じ目的を果たすため）。
- 対象エンドポイント：
  - メッセージ送信（会話進行トリガー）。`PERSONA_ONLY`モードの自動進行も内部的には同じ処理（会話を1ターン進める処理）を繰り返し呼ぶため、ここに制限をかければ自動進行のケースも合わせてカバーされる。
  - サインアップ。
  - 上記以外（ペルソナ一覧・チャット履歴・チャット削除等、LLM APIを呼ばない操作）は対象外とする。
- 具体的な閾値（例：1分あたりN回）はハードコードせず、5節の`BaseSettings`経由の設定値として持つ。初期値は実装時に決定・調整する。
- 制限超過時はHTTP 429、`{"message": "string"}`（common.md6節の形式）を返す。

### 理由

- 要件定義7節の規模（同時数十人程度、大規模アクセス対応不要）ではインメモリのレート制限で十分であり、Redis等の追加インフラはこの段階では過剰（YAGNI）。
- メッセージ送信は唯一LLM APIを呼び出す＝コストが発生する操作であり、要件の「連続送信・短時間での連発送信の制限」に直接対応する。サインアップは自己登録機能を追加したことで生じた新しい悪用面のため対象に含めた。
- ログインへの二重の制限は既存のロック機構と役割が重複するため避けた。
