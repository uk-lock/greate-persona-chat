# コーディング方針（TypeScript / Next.js / React）

対象は `frontend/` 配下。共通方針は [common.md](./common.md)。本ファイルはフロントエンド固有の内容のみを扱う。

各項目の状態表記は [common.md](./common.md) と同じ（確定／暫定／未決定／今後検討）。

---

## 1. 型の扱い（型安全性）

**状態：確定**

### ルール

- `strict: true` を採用する。
- `any` の使用は原則禁止。外部ライブラリの型定義が無い／不正確である等の例外に限り許可し、使用箇所には直前に1行コメントで許容理由を明記する（共通方針・論点4に準拠）。

### 例

```typescript
// 悪い例：理由なしのany
function parseConfig(raw: any) { ... }

// 良い例：外部ライブラリの型定義が存在しないため一時的にanyを許容
// (xxx-libがv2時点で型定義未対応のため。型定義追加時にunknownへ置き換える)
function parseLegacyResponse(raw: any) { ... }
```

## 2. 設定値・環境変数の管理

**状態：確定**

### ルール

- Next.jsの環境変数機構（`.env*`・`NEXT_PUBLIC_`プレフィックスのルール）に従う。
- `process.env` への直接アクセスは設定を集約する1箇所に閉じ込め、それ以外のコードからは直接参照しない。

### 理由

- 共通方針（論点8）の「設定値は一元管理し、直接参照しない」を、Next.jsの標準的な仕組みで実現する。

## 3. lint・format・型チェック

**状態：確定**

### ルール

- lintは既存の `eslint`（`eslint-config-next`）を継続利用する。
- formatは新たに **Prettier** を導入する。

## 4. App Routerの利用方針

**状態：確定**

### ルール

- Next.jsのApp Router（`app/`ディレクトリ）を採用する。Pages Routerは使わない。
- ルーティング・レイアウトは、`page.tsx` / `layout.tsx` / `loading.tsx` / `error.tsx` / `not-found.tsx` などの標準的な規約ファイルを中心に、基本機能の範囲で運用する。
- Route Groups・Parallel Routes・Intercepting Routesなどの高度な機能は、現時点で必要になっていないため使わない。並行表示・モーダル遷移など具体的な要件が生じた時点で導入を検討する。

### 理由

- CLAUDE.mdの開発方針「小さく作る」「過度に複雑な設計を避ける」に沿い、現時点の画面設計で必要とされていない高度なルーティング機能を先回りして採用しない。
- Next.js 16の標準構成（`create-next-app`の初期構成）がApp Routerであり、既存の`frontend/app/`構成とも一致する。

## 5. Server ComponentとClient Componentの使い分け

**状態：確定**

### ルール

- 各コンポーネントは**デフォルトでServer Component**とする。
- `useState` / `useEffect` / イベントハンドラ / ブラウザAPIなど、クライアント側の機能が必要な箇所にのみ `"use client"` を付与し、その範囲は可能な限り末端（ボタン、フォーム入力など）に留める。
- ページ全体を`"use client"`化する（ページ単位でClient Component化する）ことは行わない。

### 理由

- LLMとの対話・データ取得が中心のアプリであり、Server Component側でのデータ取得（DB/API呼び出し）と相性が良い。
- 個人開発規模でも、最初から正しい境界で書いた方が後からの手戻りが少ない。
- Next.js公式が推奨する標準的な設計であり、バンドルサイズの抑制にもつながる。

具体的な境界の引き方（フォーム全体をClientにするか、入力欄だけか等）は、論点6「ページ、レイアウト、コンポーネントの分割」と合わせて検討する。

## 6. ページ、レイアウト、コンポーネントの分割

**状態：確定**

### ルール

- Next.jsのco-location（関連ファイルを近くに置く）思想に沿い、`app/`配下を中心にコンポーネントを配置する。
- ルート専用のコンポーネントは、そのルートの`page.tsx`と同階層の `_components/`（アンダースコア始まりでルーティング対象外）に置く。
- 複数ルートで再利用するコンポーネント（ボタン・インプット等の汎用UI部品）のみ、最上位の`components/`に置く。特定機能に紐づくもの（例：`persona-card.tsx`）は最上位に上げず、使用するルート配下に留める。
- ログイン後の共通レイアウト（サイドバー）のように、複数ルートで共有するレイアウトはRoute Group（例：`(authenticated)/`）でまとめ、その配下に共通の`layout.tsx`・`_components/`を置く。Route Groupsはレイアウト共有のための基本機能として扱い、論点4で対象外とした「高度な機能」（Parallel Routes・Intercepting Routes）には含めない。

### 構成例

```text
frontend/
├── app/
│   ├── layout.tsx                    … ルートレイアウト（全体共通）
│   ├── login/
│   │   ├── page.tsx                  … S00 ログイン画面
│   │   └── _components/
│   │       └── login-form.tsx
│   ├── signup/
│   │   ├── page.tsx                  … S06 サインアップ画面
│   │   └── _components/
│   │       └── signup-form.tsx
│   └── (authenticated)/              … ログイン後画面をまとめるRoute Group
│       ├── layout.tsx                … S01〜S05共通のサイドバーレイアウト
│       ├── _components/
│       │   └── sidebar.tsx
│       ├── chats/
│       │   ├── new/
│       │   │   ├── page.tsx          … S01 新規チャット画面
│       │   │   └── _components/
│       │   │       └── persona-select-list.tsx
│       │   ├── page.tsx              … S02 チャット履歴画面
│       │   ├── _components/
│       │   │   └── chat-history-list.tsx
│       │   └── [chatId]/
│       │       ├── page.tsx          … S03 チャット画面
│       │       └── _components/
│       │           ├── message-list.tsx
│       │           └── message-input.tsx
│       └── personas/
│           ├── page.tsx              … S04 ペルソナ一覧画面
│           ├── _components/
│           │   └── persona-card.tsx
│           └── [personaId]/
│               ├── page.tsx          … S05 ペルソナ詳細画面
│               └── _components/
│                   └── persona-profile.tsx
└── components/                       … 複数ルートをまたいで再利用するもののみ
    └── ui/
        ├── button.tsx
        └── input.tsx
```

### 理由

- 共通方針（論点5）の「再利用されるか」「関心事が別か」で分割を判断する原則を、フロントエンドのディレクトリ構成に具体化したもの。
- co-locationにより、ファイルを探す際にルーティング構造と一致するため迷いにくい。`features/`のような追加の抽象化層は、複数ルートをまたぐ機能が実際に増えた段階で検討する（YAGNI）。

なお、個々のコンポーネントの責務の粒度（1コンポーネント1責務等）は、共通方針（論点5）でカバー済みのため、本ファイルでは独立した論点としては扱わない。

## 7. Presentational Componentとロジックの分離

**状態：確定**

### ルール

- Presentational（見た目）とロジック（データ取得・状態管理）を機械的に別ファイル・別コンポーネントへ分離する専用ルールは設けない。分離するかどうかは共通方針（論点5）の基準（再利用されるか、関心事が別か）に委ねる。
- ロジックが複雑になった場合や、同じ見た目を複数箇所で使い回す場合にのみ、カスタムフック等への切り出しを検討する。

### 理由

- 論点5の「関数の長さの目安50行、厳密な制約ではない」という方針と一貫させ、Presentational/Container分離を新たなルールとして追加しない。
- 論点5で決めた「`"use client"`は末端のみに付与する」という境界が、結果的にイベントハンドラ・状態を持つ部分（ロジック）を自然に切り出す力学として働くため、専用ルールがなくてもゆるい分離は実質的に機能する。

## 8. 状態管理

**状態：確定**

### ルール

- 状態管理はReactの標準機能（`useState` / `useReducer` / Context API）のみで運用し、TanStack Query・Zustand等の追加ライブラリは導入しない。
- サーバー状態（DB・APIのデータ）は、論点5の方針通りServer Component側でのデータ取得を基本とする。クライアント側で保持する状態は、フォーム入力やチャットのメッセージ送信・追加など、Client Component内で完結する範囲に留める。
- 複数コンポーネントにまたがるグローバルなクライアント状態が必要になった場合は、まずContext APIで対応する。

### 例外を認める条件

- クライアント側のキャッシュ・再検証等が具体的に必要になり、`useState`/`useReducer`での自前実装がコスト・複雑さの面で明らかに見合わない場合に限り、サーバー状態管理ライブラリの導入を検討する。現時点ではその必要性が確認できていないため導入しない（YAGNI）。

### 理由

- 論点5で「データ取得はServer Component側で行う」と決めたため、クライアント側で複雑なサーバー状態管理が必要になる場面は限定的（S03チャット画面でのメッセージ送受信程度）。
- 個人開発規模で、恩恵が限定的なライブラリを先回りして導入するのは過剰と判断した。

## 9. API通信

**状態：確定**

### ルール

- axios等のHTTPクライアントライブラリは導入せず、標準の`fetch`をベースにする。
- ベースURL・共通ヘッダ（認証情報等）の付与、および共通方針（論点6）のエラーレスポンス形式（`{"message": "string"}`）のパースをまとめた薄いラッパー関数（例：`lib/api-client.ts`）を1つ用意し、全APIコールはそこ経由で行う。個々の呼び出し箇所で生の`fetch`を直接書かない。
- Server Componentでのデータ取得ではNext.js拡張済み`fetch`のキャッシュ機構（`cache`/`next.revalidate`オプション）をそのまま利用する。

### 理由

- 論点6のエラー形式パースや認証情報の付与が全APIコールで共通して必要になるため、ラッパーなしでは重複が発生する。
- axios等が持つインターセプター・リトライ等の機能は現時点で必要性が確認できず、個人開発規模では過剰（YAGNI）。

## 10. loading、error、empty状態

**状態：確定**

### ルール

- ルート単位のloading/errorは、Next.js標準の規約ファイル（`loading.tsx` / `error.tsx`）を使う。
- Client Component内の局所的なローディング・エラー表現（フォーム送信中のボタンdisable+スピナー、送信エラーメッセージ等）は、`loading.tsx`/`error.tsx`ではカバーできないため、`components/ui/`に用意する最小限の共通部品（例：`<Spinner>`）で表現する。
- empty状態（0件表示）はNext.js標準機構の対象外のため、各ページ内でデータ件数を見て条件分岐する形で都度実装する。専用の共通コンポーネントは現時点では用意しない。

### 理由

- ルート単位の状態はNext.jsの標準機構に乗ることで、論点5（Server Component中心）と自然に噛み合い、ボイラープレートが少ない。
- Client Component内の局所的な状態はNext.js標準機構でカバーできないため、そこだけ最小限の共通部品で補う。全てを共通コンポーネントに統一すると`loading.tsx`等と役割が重複するため避けた。

## 11. フォームとバリデーション／React Hook Formなどのライブラリ利用方針

**状態：確定**

### ルール

- フォームは**React Hook Form**でフォーム状態管理を行う。
- バリデーションスキーマは**Zod**で定義し、`@hookform/resolvers`でReact Hook Formと連携する。
- 自前の`useState`＋独自バリデーション関数によるフォーム実装は行わない。

### 理由

- S00（ログイン）・S06（サインアップ）・S03（チャット送信）と既に複数のフォームがあり、今後の機能拡張でも増える見込みがあるため、共通方針（論点5）の「再利用されるか」の基準に照らして早期にライブラリへ寄せる方が重複を避けられる。
- Zodのスキーマは型安全性の方針（論点4）と相性が良く、スキーマからの型推論により型を省略せずに済む。

## 12. useEffectの利用基準

**状態：確定**

### ルール

- データ取得目的の`useEffect`は使わない。データ取得はServer Component側（論点5・9）で行う。
- `useEffect`の使用は、ブラウザAPIの購読（`addEventListener`等）や外部ライブラリとの同期など、**Reactの外の世界と同期する場合**に限定する。
- 状態の同期・派生値の計算目的で`useEffect`を使わない（レンダー中の計算や、イベントハンドラ内での更新に置き換える）。

### 理由

- 論点5（Server Component中心）・論点8（状態管理は標準機能のみ）・論点9（API通信はfetchラッパー経由）で、クライアント側でのデータ取得自体が限定的な設計にしたため、データ取得目的の`useEffect`は本来不要になる。ここで明文化し、実装・レビューで機械的にチェックできるようにする。
- React公式が示す「Effectが本当に必要なケース」の考え方に沿い、不要な再レンダリングやタイミングに起因するバグを避ける。

---

## 13. メモ化の利用基準

**状態：確定**

### ルール

- `useMemo` / `useCallback` / `React.memo`は**原則使わない**。デフォルトではメモ化せずに実装する。
- パフォーマンス上の問題が実際に確認された箇所にのみ、計測の上でメモ化を追加する。「念のため」での先回りした追加は行わない。

### 理由

- 早すぎる最適化を避けるというReact公式の方針に沿う。個人開発規模かつServer Component中心（論点5）の設計では、重い再レンダリングが起きにくく、先回りしたメモ化はコストに見合わない。
- React 19系を使用しており、将来的にReact Compilerの導入余地もあるため、手動メモ化を積み上げない方が移行コストも小さい。

---

## 14. interfaceとtypeの使い分け

**状態：確定**

### ルール

- 型定義は**`type`に統一**する。`interface`は使わない。
- オブジェクトの拡張が必要な場合は交差型（`&`）で表現する。

### 理由

- 論点11でZodを採用し、型はスキーマから`z.infer<typeof schema>`で導出する運用が中心になるため、`type`に統一した方が一貫する。
- 宣言マージ・`implements`対象化など`interface`固有の機能を必要とする場面がこのプロジェクトでは想定されず、使い分けの判断コストだけが残る。

## 15. カスタムフックの利用基準

**状態：確定**

### ルール

- 同じ状態＋ロジックの組み合わせを2箇所以上で使う場合は、カスタムフックへ切り出す。
- 単一責務の原則（論点5）に照らして、1つのコンポーネント内でロジック部分が明らかに肥大化している場合も、切り出しを検討する。
- 具体的な数値基準（`useState`の個数等）は設けない。あくまで定性的な目安として運用する。

### 理由

- 論点7で「ロジックが複雑になった場合はカスタムフックへの切り出しを検討する」とした基準を具体化したもの。
- 数値基準を細かく置くと、共通方針（論点5）の「厳密な制約ではなく参考値」というトーンと矛盾するため、定性的な基準に留めた。

## 16. propsの設計

**状態：確定**

### ルール

- propsの型は、コンポーネント名に対応する `type Props = {...}` として定義する。必要なデータのみを渡し、オブジェクトを丸ごと渡さない。
- boolean propsを濫用しない。同じコンポーネントで3個以上の真偽値フラグによって表示を出し分けることはせず、その場合はUnion型のvariant（例：`variant: "default" | "compact"`）や、コンポーネント自体の分割を検討する。
- イベントハンドラを受け取るpropsは `onXxx`（例：`onSubmit` / `onSelect`）の形式で命名する。

### 例

```typescript
// 悪い例：boolean propsの濫用
type Props = {
  isCompact: boolean;
  isHighlighted: boolean;
  isDisabled: boolean;
};

// 良い例：variantで出し分ける
type Props = {
  variant: "default" | "compact" | "highlighted";
  disabled: boolean;
};
```

### 理由

- propsはコンポーネント間の「契約」であり、他の論点（型・エラー処理等）と同様に良い例・悪い例を示すことで、AIによる実装時の一貫性を保つ。
- boolean propsの濫用・命名規則の不統一は、Reactの実装で典型的に発生しやすい問題であり、機械的にチェックしやすい基準として明記する価値がある。

## 17. CSSおよびスタイリング

**状態：確定**

### ルール

- スタイリングは**Tailwind CSS**のユーティリティクラスをJSX内に直接記述する方式に統一する。CSS Modules・CSS-in-JS等は導入しない。
- 繰り返し使うスタイルの組み合わせは、独自の抽出用ライブラリで解決せず、論点6の`components/ui/`へのコンポーネント化によって重複を吸収する。
- 条件付きクラス結合が必要な場合、`clsx`程度の小さな補助ライブラリの利用は許容する。導入が必要になった時点で判断する。

### 理由

- 既にセットアップ済みのTailwindをそのまま使い、追加導入コストをゼロにする。
- Tailwindはマークアップ（JSX）とスタイル値が同じファイルに同居する（CSS Modulesにしても`className`参照はJSX側に残り、完全分離にはならない）。個人開発規模でデザインとロジックをファイルレベルで分離する必要性は薄く、コンポーネント化（論点6）による重複抑制で十分と判断した。

## 18. アクセシビリティ

**状態：確定**

### ルール

- 既存の`eslint-config-next`に同梱される`eslint-plugin-jsx-a11y`のデフォルトルールに従う（push前lintで機械チェックされる）。
- 加えて、以下の3点は実装時に明示的に守る。
  - フォームの入力欄には`label`を関連付ける。
  - アイコンのみのボタン・リンク（サイドバー等）には`aria-label`を付ける。
  - `<img>`には`alt`（代替テキスト）を付ける。
- WCAG準拠レベルの指定等、上記を超える独自基準は現時点では設けない。必要になった時点で追加する。

### 理由

- 画面一覧（S00〜S06）を踏まえると、サイドバー（アイコンのみ表示）・フォーム・ペルソナのアバター画像が主な該当箇所になるため、そこに直結する最低限の3点に絞った。
- lintで機械的に検出できない観点（label関連付け、aria-label等）を明文化することで、AIによる実装時にも意識されやすくする。

## 19. テスト

**状態：確定**

### ルール

- テストランナーは**Vitest**、コンポーネントのレンダリング・操作検証には**React Testing Library**（RTL）を使う。
- 共通方針（論点9）の「ビジネスロジック」に該当する部分（Zodバリデーションスキーマ、カスタムフックのロジック部分等）は単体テストで担保する。
- 「主要フロー」に該当する部分（フォーム送信〜エラー表示等）は、Client Component単位の結合的な検証としてRTLでテストする。
- Server Component自体は直接テストの対象としない。データ取得・変換等のロジックは、Server Componentから純粋な関数として切り出し、その関数を単体テストする。
- テストコードの配置は共通方針（論点11①）の通り、`tests/`配下にソースのディレクトリ構造をミラーリングする。

### 理由

- Vitestは実行速度・設定のシンプルさで優れ、バックエンドの`pytest`と同様の位置付けで採用する。
- RTLは「実装の詳細でなくユーザー操作の観点でテストする」という思想がReact公式からも案内されており、業界標準に近い。
- Server Componentの直接テストは、現状ツールの対応が発展途上であるため対象外とし、ロジック部分を関数として切り出すことでテスト容易性を確保する。

## 20. セキュリティ上の注意点

**状態：確定**

### ルール

- `dangerouslySetInnerHTML`は原則使用しない。ペルソナ発言（LLM出力）・ユーザー入力ともに外部由来のテキストであり、Reactの標準エスケープに任せてプレーンテキストとして描画する。Markdown等のリッチレンダリングが将来必要になった場合も、サニタイズ済みの専用ライブラリ経由に限定し、生のHTML挿入は行わない。
- `NEXT_PUBLIC_`プレフィックスの環境変数には、APIキー等の秘密情報を置かない（論点2の具体化。`NEXT_PUBLIC_`はクライアントバンドルに埋め込まれ誰でも参照可能なため）。
- 認証トークンをlocalStorage/sessionStorageに自前で保存しない。認証はJWTのHttpOnly Cookie方式（[api.md](/workspace/docs/api.md)）に委ね、API通信のfetchラッパー（論点9）はCookieがブラウザから自動送信される前提で実装する。

### 対象外（今後検討）

- CSRF対策（Cookieの`SameSite`属性設定等）は、API・バックエンド側の設定に依存するため本ファイルの範囲外とする。バックエンド側またはフロントエンド/バックエンド境界の論点として今後扱う。

### 理由

- ペルソナのLLM発言をそのまま`innerHTML`的に描画するコードは蓄積型XSSに直結するリスクが高く、AIによる実装時に誤って書かれやすいため明記する価値が高い。
- HttpOnly Cookie方式というAPI側の安全な設計を、フロントエンド側の実装（トークンの自前保存等）で台無しにしないための確認。

## 21. 関数の宣言方法

**状態：確定**

### ルール

- 関数は`function`宣言ではなく**アロー関数**で統一する。Reactコンポーネント・Server Action・通常のユーティリティ関数のいずれも対象とする。
- `export default`が必須なファイル（`page.tsx`/`layout.tsx`等のNext.js規約ファイル）では、アロー関数を`const`で定義した上で`export default`を別行で行う。

### 例

```typescript
// 悪い例：function宣言
export function loginAction(values: LoginFormValues) { ... }

// 良い例：アロー関数
export const loginAction = async (values: LoginFormValues) => { ... };
```

### 理由

- プロジェクト内で記法を統一し、レビュー・実装時の迷いをなくす。`function`宣言・アロー関数のいずれも機能的な差はこのプロジェクトの用途では問題にならないため、統一のみを目的とする。
