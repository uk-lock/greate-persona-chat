# コーディング方針（共通）

対象は `frontend/`（TypeScript / Next.js / React）・`backend/`（Python / FastAPI）。
言語固有の方針は [backend-python.md](./backend-python.md)・[frontend-typescript-react.md](./frontend-typescript-react.md) を参照。

各項目には状態を付す。

- **確定**：このまま運用する
- **暫定**：運用しつつ見直す可能性がある
- **未決定**：今後決める
- **今後検討**：優先度が低く、後回しにする

## 1. コーディング方針の目的と適用範囲

**状態：確定**

### 目的

このプロジェクトの実装は Claude Code（AI）が主体的に担う比重が大きいため、本方針書は以下の両方を満たす形で書く。

- **AIが実装・レビュー時に機械的に遵守・チェックしやすいこと**：ルールは短く断定的に書き、可能な範囲で良い例／悪い例を添える。
- **人間（開発者自身）が読んでも理由が分かること**：各ルールに「なぜそのルールを採用するか」を1行程度で添える。

長い解説文や背景説明中心の文書にはしない。ルール→理由→（必要なら）例、という形式を基本とする。

### 適用範囲

`frontend/`・`backend/` 配下で **Git管理されているソースコード全体**（アプリケーションコード・テストコードを含む）に適用する。

`node_modules`・ビルド生成物（`.next/` 等）はそもそもGit管理対象外であり「成果物」とみなさないため、除外リストとして明記する対象にも含めない（管理していないものを除外すると書く必要がない、という整理）。

自動生成コード（例：マイグレーションファイルの自動生成部分、OpenAPIクライアントの自動生成コード等）が今後発生した場合は、発生した時点で本書に除外規定を追記する（未発生の段階で先回りして規定しない）。

## 2. 命名規則（ドメイン用語）

**状態：確定**

### ルール

- 変数名・関数名・DBカラム名・API項目名などの識別子は、ドメイン用語も含めて**英語で統一する**。日本語のローマ字表記（例：`ijin`）は用いない。
- 用語に迷った場合は、まず既存ドキュメント（[requirements-definition.md](../requirements-definition.md)・[db.md](../db.md)・[api.md](../api.md)・`docs/screens/`配下）で使われている表記に合わせる。
- ドキュメント側にも表記がなく、なお迷う場合は、ルールを先回りして決めずに**実装時に都度会話で確認する**。

### 理由

- 既存の `docs/db.md`・`docs/api.md` の時点で `m_user` / `t_chat` / `chat_mode` / `PERSONA_ONLY` など英語ベースの命名が既に採用されており、実態に合わせた。
- 個人開発規模のプロジェクトで想定しきれない命名ケースを事前に全て規定するのはコストに見合わないため、既存ドキュメントを一次情報源としつつ、例外は都度判断する運用とする。

### 参考：既存ドキュメントで確定している主要用語

| 日本語 | 識別子 | 出典 |
|---|---|---|
| ペルソナ | `persona` | [db.md](../db.md) `m_persona` |
| チャット | `chat` | [db.md](../db.md) `t_chat` |
| チャットモード | `chat_mode` | [db.md](../db.md) / [api.md](../api.md) |
| メッセージ | `message` | [api.md](../api.md) |
| ユーザー | `user` | [db.md](../db.md) `m_user` |
| ログインID | `login_id` | [db.md](../db.md) `m_user` |

## 3. コメント・ドキュメンテーションの書き方

**状態：確定**

### ルール

- 関数（メソッド含む）には**基本的にdocstring（要約コメント）を付与する**。何をする関数かを短く書く。
- 複雑な処理や、コードだけでは意図が伝わりづらい処理には、その処理の**直前に1行コメント**を付ける（WHY・非自明な制約・意図を書く）。単純な処理には付けない。
- docstring・コメントの説明文は**日本語**で統一する（識別子自体は論点2の通り英語統一のまま）。
- コメントを最小限にする一方で、**型情報は省略しない**（型ヒント・型注釈を必ず付与する）。

### 理由

- 実装の多くをAI（Claude Code）が担うため、関数単位でdocstringがあると、実装・レビューの双方が本文を読まずに関数の役割を把握できる。
- 複雑な処理にのみ1行コメントを絞ることで、コードとコメントの乖離（コードは変更されたがコメントが古いまま残る）のリスクを、単純な処理については避けられる。
- コメントを最小限にする分、型注釈が唯一の「機械的に検証可能な仕様」になる。型を省略すると非自明な仕様がコードにもコメントにも残らなくなるため、型ヒントの徹底を明文化した。

## 4. 型の扱い（型安全性）

**状態：確定**

### ルール

- 型チェックは厳格に扱う。`Any` / `any`のような「逃げ道」の使用は原則禁止し、`unknown`＋型ガード等で代替する。
- 外部ライブラリの型定義が無い／不正確である等、原則に従えない例外に限り `Any` / `any` の使用を許可する。その場合は必ず直前に1行コメントで**許容理由**を明記する（論点3のコメント規約に準拠）。理由のない `Any` / `any` は不可とする。

### 理由

- 論点3で「型がコメント代わりに機能する」方針を決めたため、型が緩いと肝心の仕様がどこにも残らなくなる。
- 一切禁止にすると、外部ライブラリ由来でどうしても型が取れないケースで実装が詰まるため、コメント必須の例外を設け現実的な運用にする。
- 例外に理由コメントを必須にすることで、「なんとなく `any`」のなし崩し的な多用を防ぐ。

## 5. 関数・クラス・コンポーネントの責務／ファイル分割の基準

**状態：確定**

### ルール

- 責務・ファイル分割の基準は**実用的な粒度**とする。単一責務を原則としつつ、密接に関連する小さなヘルパー等は同一ファイルへの同居を許容する。
- ファイルを分けるかどうかは、行数ではなく「他の場所から再利用されるか」「関心事が別か」を優先して判断する。
- 関数の長さの目安として**50行**を置くが、これは厳密な制約ではなく参考値であり、強制度合いは高くない。50行を超えたら即分割ではなく責務が混ざっていないか・可読性が損なわれていないかを都度判断し、逆に50行未満でも責務が混在していれば分割する。
- 1ファイルは「1つの責務のまとまり」を表す単位とする（例：1つのユースケース、1つのReactコンポーネントとその専用の小さなサブコンポーネント）。

### 理由

- CLAUDE.mdの開発方針「小さく作る」「過度に複雑な設計を避ける」と、基本姿勢の「責務分離」「AIによる実装・レビューのしやすさ」の両方を満たすバランスを取るため。
- 行数を絶対基準にすると、機械的な分割によってかえって責務が分断され読みにくくなるケースがあるため、目安に留める。

## 6. エラーハンドリングの基本方針

**状態：確定**

### ルール

- APIのエラーレスポンス形式は `{"message": "string"}` を標準とする（既存の [api.md](../api.md)・[S00-login.md](../screens/S00-login.md)・[S06-signup.md](../screens/S06-signup.md) と同じ形式）。エラー種別ごとの機械可読な `code` フィールドは現時点では設けない。

### 例外を認める条件

- フロントエンドがエラー種別ごとに機械的な分岐処理を必要とする具体的なケースが生じた場合に限り、`code` フィールドを**後方互換の形で追加**してよい（既存の `message` フィールドの意味は変えない）。現時点ではその必要性が確認できていないため導入しない（YAGNI）。

### 理由

- 「小さく作る」「動くもの優先」の方針に沿い、具体的な必要性が出てから機械可読コードを追加する。既存ドキュメントとの一貫性も保てる。

## 7. ログ出力の基本方針

**状態：確定**

### ルール

- ログは**構造化ログ（JSON）**形式で出力する。1行1JSONとし、最低限 `timestamp` / `level` / `message` を含める。
- 出力先は標準出力（コンテナのstdout）とし、クラウド側のログサービスでの収集・検索を前提とする。専用のログ集約基盤（ELK等）は自前で構築しない。

### 理由

- 要件定義7節「運用は最小限、ログで状況確認できれば十分」の方針のもと、監視基盤は作らない一方、クラウド運用が前提のためログ形式だけJSON化しておくことで、将来の状況確認コストを下げられる。
- 軽量なロギング設定で足り、過度な監視基盤の構築にはあたらない。

## 8. 設定値・環境変数の管理／マジックナンバーの扱い

**状態：確定**

### ① 設定値・環境変数の管理

- 設定値は一元管理し、コード中で環境変数を直接参照しない。

理由：論点4の型安全性の方針と一貫させ、設定値の一覧性とテスト時のモックしやすさを確保するため。

### ② マジックナンバー・固定文字列の扱い

- ドメイン上意味を持つ数値・文字列（ロック時間、失敗回数上限、ページング件数、`chat_mode`の値等）は名前付き定数として定義し、リテラル値を直接コードに埋め込まない。
- UI都合の些細な値（デバウンス時間等）は都度判断でよく、一律の定数化は求めない。
- 定数はドメイン上の仕様に紐づくものが多いため、可能な範囲で `docs/db.md` 等の記述と対応が取れる名前・値にする。

理由：要件・DB設計上「仕様」として意味を持つ値を1箇所に集約し、仕様変更時の追随漏れを防ぐため。個人開発規模でリテラル値を全面禁止するのは過剰と判断し、意味のある値に絞った。

## 9. テスト方針（共通レベル）

**状態：確定**

### ルール

- ビジネスロジック（ロック判定、`chat_mode`分岐、バリデーション等）は**単体テスト**で担保する。
- 認証・チャット等、複数レイヤーをまたぐ主要フローは**結合テスト**で担保する。
- ブラウザ経由のE2Eテスト（Playwright等）は現時点では対象外とする。将来必要になった時点で追加を検討する。

### 理由

- 個人開発規模で投資対効果が高い範囲（ビジネスロジック＋主要フロー）に絞る。

## 10. lint・format・型チェックの運用

**状態：確定**

### ルール

- lint・format・型チェックは、フロントエンド・バックエンドともに**push前（pre-push）に自動実行**する。コミット単位では強制しない。
- 実装には**Husky**（Node/npmベース）を採用する。フロントエンドが既にnpm運用のため、pre-pushフック1本でバックエンド・フロントエンド両方のチェックをシェルコマンドとして呼び出す。
- CI（GitHub Actions等）での強制は現時点では構築しない。将来必要になった時点で追加を検討する。

### 理由

- 既存の依存関係（frontendの`eslint`／`strict`なtsconfig）を活かし、追加ツールを最小限に抑える。
- コミット単位での強制は個人開発の作業速度を妨げやすいため見送り、共有前（push前）にのみチェックを効かせることで「壊れたコードをリモートに送らない」という実利を確保する。
- モノレポ構成上、Node/npmベースのHuskyであれば言語をまたいで1つの仕組みで完結できる。

## 11. ディレクトリ構成（テスト配置）／方針書のファイル構成

**状態：確定**

### ① テストコードの配置

- バックエンド（Python）・フロントエンド（TS/React）**ともに**、テストコードは `tests/` 配下にソースのディレクトリ構造をミラーリングして配置する（ソースファイルとの同居はしない）。

理由：言語ごとの主流に合わせて使い分けるより、モノレポ全体でテストの置き場所を統一した方が「テストがどこにあるか」を迷わず探せるため、一貫性を優先した。
