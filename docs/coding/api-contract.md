# コーディング方針（API契約：フロントエンド/バックエンドの境界）

対象は`frontend/`と`backend/`の間の約束事。各stack内で閉じる内容は[common.md](./common.md)・[backend-python.md](./backend-python.md)・[frontend-typescript-react.md](./frontend-typescript-react.md)を参照。

各項目の状態表記は[common.md](./common.md)と同じ（確定／暫定／未決定／今後検討）。

---

## 1. API契約の管理方法／型の共有方法／OpenAPIの利用方法

**状態：確定**

### ルール

- FastAPIが自動生成する**OpenAPIスキーマを正**とする。フロントエンド側でリクエスト/レスポンスの型を手書きで二重定義しない。
- バックエンドの`backend/scripts/export_openapi.py`でOpenAPIスキーマをJSONとして出力し、`openapi-typescript`でTypeScript型を生成する。

```bash
python backend/scripts/export_openapi.py > openapi.json
npx openapi-typescript openapi.json -o frontend/lib/api-types.gen.ts
```

- 生成するのは**型定義のみ**。リクエスト送信ロジックまで生成するフルクライアント（`orval`等）は導入しない。
- 生成ファイルは`.gen.ts`のようなサフィックスを付け、生成物であり手編集しないことが分かるようにする。CIは構築していない（common.md10節）ため、バックエンドのAPIを変更した開発者が**手動で再生成**する。
- 生成ファイルはGitに**コミットする**（コミットしないと、フロントのみを触る際にバックエンドを起動しないとビルドできなくなるため）。

### 理由

- バックエンドのPydanticスキーマ（backend-python.md9節）とフロントの型を二重管理すると、変更のたびに両方を手で直す必要が生じ、ドリフト（型の食い違い）のリスクが高い。FastAPIは元々OpenAPIスキーマを自動生成する機能を持つため、追加の手間は生成コマンドを1つ用意するだけで済む。
- フルクライアント生成は、Next.js側のAPI呼び出し方針（フロントエンド側で別途検討）を先取りして固定してしまうことになるため、この段階では型のみに留める。
- CI未構築の現状に合わせ、生成は手動運用とする。将来CIを構築する段階で自動化を検討する（今後検討）。

## 2. エラーレスポンスの型の扱い

**状態：確定**

### ルール

- エラーレスポンスの形（`{"message": "string"}`、common.md6節）は、OpenAPIスキーマ（および1節の自動生成型）の対象に**含めない**。各バックエンドエンドポイントに`responses={...}`を追加する対応は行わない。
- フロントエンド側で、この固定形状を手動で1つの共通型（例：`ApiErrorResponse`）として定義し、全APIのエラーハンドリングで共通利用する。

### 理由

- エラー形式は`{"message": "string"}`で固定されており（`code`フィールドを追加する条件も明文化済み）、ほとんど変化しない単純な形なので、手動定義のメンテナンスコストは低い。
- 型安全性のためだけに、全エンドポイントの実装（`responses=`宣言）へ影響を与えるのは費用対効果が見合わないと判断した。

## 3. 命名の統一（フロント⇔バックエンド）

**状態：確定**

### ルール

- API通信（wire format）は**snake_case**（Pythonの慣習、既存docsの表記と一致）のまま変えない。
- フロントのAPIクライアント層（fetchラッパー）の境界で変換する。
  - レスポンス受信時：`camelcase-keys`でsnake_case→camelCaseに変換し、呼び出し側にはcamelCaseの値・型を返す。
  - リクエスト送信時：`snakecase-keys`でcamelCase→snake_caseに変換してから送信する。
- 手書きの重複した型は作らない。1節で自動生成したsnake_caseの型を`camelcase-keys`／`snakecase-keys`の型変換に通すことで、camelCase版の型を導出する。
- APIクライアント層より内側（コンポーネント・状態管理等）は一貫して**camelCase**を使う。

### 理由

- バックエンド（Python/DB）とフロント（TS/JS）それぞれの言語慣習に沿った命名を保ちつつ、境界で変換することでどちらの慣習も崩さない。
- `camelcase-keys`／`snakecase-keys`は型変換も提供するため、手書きの重複した型を用意する必要がなく、1節で決めたOpenAPIベースの自動生成の恩恵をそのまま受けられる。

## 4. 日時の形式

**状態：確定**

### ルール

- API通信での日時は**ISO 8601文字列（UTC）**とする（例：`"2026-07-24T12:34:56Z"`）。Pydantic（FastAPI）のデフォルトのシリアライズ形式をそのまま使い、追加の変換設定はしない。
- サーバー・DB側は常に**UTC**で保持・送信する（`db.md`の`DATETIME`列もUTC格納が前提）。
- ユーザーのローカルタイムゾーンへの変換は、表示のためだけにフロントエンドで行う（具体的な変換方法はfrontend-typescript-react.mdで別途定める）。

### 理由

- FastAPI/Pydanticの標準の挙動そのままで済み、余計な設定が不要。人間にも読みやすくデバッグしやすい。
- UTCで一元管理することで、将来ユーザーが異なるタイムゾーンからアクセスしても、サーバー・DB側のロジックに時差の考慮を持ち込まずに済む。

## 5. nullと未定義値の扱い

**状態：確定**

### ルール

- APIレスポンスで値が存在しない場合は、明示的に`null`を返す（キー自体は省略しない）。Pydantic/FastAPIのデフォルトの挙動に従い、`exclude_none`等の設定はしない。
- フロントのTypeScript型では、APIから来るデータの「値なし」は`T | null`で表現する。`undefined`は、APIレスポンスをまだ受け取っていない等、フロントのローカルな状態専用として予約し、APIデータの型には使わない。

### 理由

- Pydantic/FastAPIの標準の挙動のままで済み、1節・4節と同じく「標準の挙動に乗ることで追加設定を増やさない」方針と一貫する。
- `null`と`undefined`の意味を分けることで、「APIが明示的に値なしと返した」のか「まだデータを取得していない」のかをコード上で区別できる。

## 6. バリデーションの責務分担

**状態：確定**

### ルール

- **バックエンドが常に唯一の正**とする。すべてのリクエストはバックエンド側で必ずバリデーションする（フロントが何を検証していたかに関わらず、サーバー側は信用しない前提で検証する）。
- **フロントエンドの検証はUX目的のみ**：必須項目、文字数上限、文字種等の「即座にフィードバックできる」項目に限り、フロント側でも検証してよい。
- フロント・バックエンドで同じ簡単なルール（文字数上限等）が重複することはあるが、これは意図的なUX上の重複であり、「ビジネスロジックの二重管理」とは区別する。DBアクセスを伴う検証（重複チェック等）やビジネスルールは、フロント側では再現せずバックエンドのみで行う。

### 理由

- クライアント側の検証は改ざん・バイパスが可能なため、セキュリティ・データ整合性の観点では意味を持たない。バックエンドを唯一の正とすることを明文化する。
- 既存の画面定義（[S00-login.md](../screens/S00-login.md)・[S06-signup.md](../screens/S06-signup.md)）で採用済みの考え方と一貫させ、新しい画面でも同じ判断基準を使えるようにする。

## 7. 認証・認可の責務分担

**状態：確定**

### ルール

- **認証の実体**（JWTの発行・検証、秘密鍵の管理）は完全にバックエンドの責務とする。フロントエンドはJWTの中身を検証せず、秘密鍵も共有しない。
- フロントエンド（Next.jsのmiddleware等）は、認証Cookieの**存在有無だけを見る軽量な判断**に留め、画面遷移（未ログイン向け画面へのアクセスガード等）のUX目的にのみ使う。実際の正当性はAPI呼び出し時にバックエンドが検証し、401が返ってきたらログイン画面へリダイレクトする。
- **認可**（自分が作成したチャットしか操作できない等の権限チェック）は完全にバックエンドの責務とする（`api.md`の「他ユーザーが作成したチャットには403を返す」という既存の記述通り）。
- フロントエンドは「権限がない操作のボタンを非表示にする」程度のUX上の出し分けをしてよいが、これはあくまで利便性のためであり、バックエンド側の権限チェックを省略する理由にはならない。

### 理由

- 6節の「バックエンドが唯一の正」という考え方を認証・認可にも一貫して適用する。
- バックエンドの秘密鍵をフロントと共有すると、秘密情報の管理箇所が増え、15節のセキュリティ方針とも矛盾する。

## 8. API変更時の運用

**状態：確定**

### ルール

- URLパスバージョニング（`/v1/`等）やヘッダーベースのバージョニングは導入しない。フロントエンド・バックエンドは常にペアでデプロイし、破壊的変更時も両方を同時にリリースする。
- 変更時の手順：
  1. バックエンドにAPI変更を実装する
  2. OpenAPIスキーマ・フロントの型を再生成する（1節のコマンド）
  3. 再生成後にフロントのビルド・型チェックでエラーが出た箇所を修正する
  4. バックエンド・フロントをまとめて同時にデプロイする

### 理由

- このAPIは第三者への公開や、更新タイミングの異なる複数クライアント（モバイルアプリ等）を想定しておらず、フロントエンドは常に最新のバックエンドとペアで動く構成のため、複数バージョンの並行維持は不要（YAGNI）。将来外部公開APIとして提供する場合に再検討する。
- 1節の型自動生成により、破壊的変更はフロントのビルドエラーとしてすぐ表面化するため、追加のバージョニング機構がなくても変更漏れに気づける。
